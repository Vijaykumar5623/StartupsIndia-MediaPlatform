# Development Guide

How to work on the StartupsIndia app without breaking existing flows. Read this
alongside [ARCHITECTURE.md](ARCHITECTURE.md) (how the app is built) and
[../CONTRIBUTING.md](../CONTRIBUTING.md) (branches, commits, PR checklist).

---

## 1. Development workflow

1. Pull `main`, create a branch (`feat/…`, `fix/…`, `docs/…`).
2. Make one small, focused change.
3. Run `flutter analyze` and `dart format .`.
4. Run the app and manually test the affected screen ([testing-guide.md](testing-guide.md)).
5. Update the relevant doc if behavior/data/decision changed.
6. Commit (Conventional Commits) and open a PR.

Keep changes small. Large, multi-feature changes are hard to review and are the
main way this codebase drifts.

## 2. Project structure (where things live)

Full layout is in [ARCHITECTURE.md](ARCHITECTURE.md). The short map:

```
lib/
├── main.dart                 # App entry: Firebase init, FCM, routes
├── firebase_options.dart     # Generated FlutterFire config (do not hand-edit)
├── theme/                    # AppColors, AppTypography, light/dark themes
├── core/                     # Shared models, providers, repositories, widgets, utils
│   └── config/app_config.dart  # Build-time config (ENV, Cloudinary)
└── features/<feature>/
    ├── data/repositories/    # Firestore / data access implementations
    ├── domain/models/        # Feature models
    ├── domain/repositories/  # Repository interfaces (when present)
    └── presentation/
        ├── providers/        # Riverpod providers
        ├── screens/          # Screens
        └── widgets/          # Feature widgets
```

Features today: `auth`, `onboarding`, `home`, `explore`, `community`, `profile`,
`bookmark`, `build`, `notifications`.

### Do not edit casually

- `firebase_options.dart` — generated by `flutterfire configure`; regenerate,
  don't hand-edit.
- `android/app/build.gradle.kts` `applicationId` / `namespace` (`in.startupsindia.app`)
  — changing this breaks Firebase and Play identity.
- `firestore.rules` / `firestore.indexes.json` — changing these needs a deploy
  (`firebase deploy --only firestore:rules`) and doc updates in [DATA_CONTRACTS.md](DATA_CONTRACTS.md).
- Platform folders (`ios/`, `macos/`, `windows/`, `linux/`, `web/`) — mostly
  generated; only touch when you know why.

## 3. How to add a new screen

1. Create the screen under `lib/features/<feature>/presentation/screens/`.
2. Register a named route in [../lib/main.dart](../lib/main.dart) `routes: { … }`.
   Follow the existing pattern for reading `ModalRoute` arguments if the screen
   takes data.
3. Navigate with `Navigator.pushNamed(context, '/your-route', arguments: …)`.
4. Use `AppColors` / `AppTypography`, not hardcoded styling.

> Historically, an unregistered `/search` route caused a crash. Always register
> the route when a screen is reachable via `pushNamed`.

## 4. How to add a widget / component

- Feature-specific → `lib/features/<feature>/presentation/widgets/`.
- Reusable across features → `lib/core/presentation/widgets/`
  (e.g. `AppTextField`, `SearchTextField`, `ShimmerPlaceholder`).
- Prefer composing existing widgets over adding a new near-duplicate. Search
  before you create.

## 5. How to add / update assets

1. Put the file under `assets/` (`images/`, `icons/`, `flags/`, `startupsindia/`).
2. Ensure the folder is declared in [../pubspec.yaml](../pubspec.yaml) `flutter.assets`.
3. Reference by path; run `flutter pub get` if you added a new folder.

## 6. How to add data / API calls

- Never call Firebase directly from a widget where it can be avoided. Add a
  method to the appropriate repository (`FirestoreRepository`,
  `CommunityRepositoryImpl`, `PostRepository`, etc.) and expose it via a Riverpod
  provider.
- Follow the existing provider styles (see [ARCHITECTURE.md](ARCHITECTURE.md) →
  State Management): `Provider` for repos, `StreamProvider` for realtime,
  `FutureProvider` for one-shot/debounced reads, `NotifierProvider` for local
  state.
- If you change a Firestore shape, update [DATA_CONTRACTS.md](DATA_CONTRACTS.md)
  and `firestore.rules`/`firestore.indexes.json` in the same change.

## 7. Loading / error / empty states

Every data-backed screen should handle all three. For `AsyncValue` from Riverpod
use `.when(data:…, loading:…, error:…)`. Use `ShimmerPlaceholder` for loading and
a clear empty state instead of an indefinite spinner. (Improving remaining
empty/error states is an open item — see [known-issues.md](known-issues.md).)

## 8. Avoiding broken flows

- Test the **auth/onboarding path** after any change near splash, login, signup,
  role selection, or profile — it gates the whole app.
- Guest mode: protected actions should route through `GuestGate` / auth checks,
  not write to Firestore directly.
- Don't remove or rename existing named routes without updating every
  `pushNamed` call site.

## 9. Code style

- `flutter_lints` via [../analysis_options.yaml](../analysis_options.yaml).
- `dart format .` before committing.
- Match surrounding naming and structure. Don't introduce a second state
  management or navigation pattern.
- The repo is **not** lint-clean yet (known warnings exist). Do not add new
  warnings; treat new **errors** as blockers.
